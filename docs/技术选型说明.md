# NimbusDrive 技术选型说明

> 状态：已定稿 | 日期：2026-08-17
> 本文回答"为什么核心链路用 sqlx 手写 SQL 而不用 GORM"，以及未来在什么条件下升级。
> 配套文档：《实现方案》第三章、《开发路线图_v1.md》。

---

## 一、现状速览

NimbusDrive 的数据访问层是**双轨制**：

| 模块 | 技术 | 职责 | 位置 |
|------|------|------|------|
| 核心链路（用户/文件/上传会话/分享） | **sqlx + pgx**，手写 SQL | 用户端数据权威，高频高并发 | `internal/store/` |
| 管理后台 | **GORM** | CRUD 为主，AutoMigrate 便利 | `internal/adminstore/` |

二者严格分层，不混用。`Store`（`internal/store/store.go`）持有 `*sqlx.DB`，`adminstore.DB`（`internal/adminstore/adminstore.go`）持有 `*gorm.DB`，两套连接池独立。

## 二、为什么核心链路选 sqlx 手写 SQL

### 2.1 连接池性能：与 GORM 同源，无差异

常见误解："手写 SQL 像原生 JDBC，每次查询开关连接有性能问题。"

事实：`*sqlx.DB` 内部就是 `*database/sql.DB`，**自带连接池**。业务代码调 `GetContext` / `SelectContext` / `ExecContext` 时：

1. 从池中借空闲连接
2. 执行查询
3. 自动归还池（不断开）

连接的真正建立/关闭只在池扩缩容时发生，业务代码不碰连接生命周期。GORM 底层同样是 `database/sql`，**连接池机制完全相同，没有性能差异**。

事务同理：`BeginTxx` 借连接持有到 `Commit`/`Rollback`，`defer Rollback` 保证归还（见 `upload_handler.go:467` 的 `withTx`）。

唯一会泄漏连接的是忘 `rows.Close()`——但 sqlx 的高阶 API（`GetContext`/`SelectContext`）内部已关闭 rows，只有手动 `QueryxContext` 遍历时才需要管。本项目核心链路全用高阶 API，无泄漏风险。

### 2.2 复杂 SQL 表达力：GORM 在核心场景要退回 Raw

核心文件链路的 SQL 本来就复杂，举几个真实例子：

```sql
-- 递归 CTE 删除子树（SoftDeleteRecursive）
WITH RECURSIVE subtree AS (
  SELECT id FROM files WHERE id = $1
  UNION ALL
  SELECT f.id FROM files f JOIN subtree s ON f.parent_id = s.id
)
UPDATE files SET deleted_at = now() WHERE id IN (SELECT id FROM subtree)

-- 原子配额更新（条件 UPDATE）
UPDATE users SET used_storage = used_storage + $2
WHERE id = $1 AND used_storage + $2 <= storage_quota

-- PG 特性的 RETURNING
INSERT INTO files (...) VALUES ($1..$10) RETURNING id
```

这些在 GORM 里要么写 Raw SQL（`db.Raw(...)`），要么用链式 API 拼不出来。既然核心查询都得回 Raw，GORM 的"省代码"优势就消失了——**手写 SQL 反而比"半链式半 Raw"更一致**。

### 2.3 行为可预测性：SQL 全可见

GORM 的链式查询 `.Where().Order().Limit()` 出错时，要在脑子里翻译回 SQL 才能调试——你在用 SQL 的心智模型，却不直接看 SQL。手写 SQL 则所见即所得，复杂链路（上传/下载/配额扣减）的 SQL 行为完全可见，对排查和性能调优更友好。

## 三、承认的代价

不辩护，诚实列出 sqlx 的真实短板：

### 3.1 列名常量手动同步（最直接的耦合点）

`internal/store/file.go` 顶部：

```go
const fileCols = `id, user_id, parent_id, name, size, mime_type, is_folder, hash_sha256,
    chunk_count, status, storage_path, deleted_at, created_at, updated_at`
```

加字段时要同步改：迁移脚本 → `domain.FileNode` 的 `db:"..."` tag → 这个 `fileCols` 常量 → 相关 INSERT 的列名与 `$1..$N` 占位符。GORM 只需前两步，省去列名同步。

**但差距是"改一行常量"vs"不改"，不是数量级差异**，且 grep 能改全。以当前表数量（files/users/file_hashes/upload_sessions/shares 共 5 张）和字段稳定度，成本可控。

### 3.2 数据库方言绑定

`RETURNING`、`WITH RECURSIVE`、`$1` 占位符都是 PG 特性。换到 MySQL 要改 SQL。GORM 能抹平方言差异，**这一项是 GORM 的真优势**。

但 NimbusDrive 从设计就钉死 PostgreSQL（依赖递归 CTE、部分索引、JSONB），换库概率为零，这个抽象成本永远收不回来。

## 四、对比结论

| 维度 | sqlx（现状） | GORM | 判断 |
|------|------------|------|------|
| 连接池性能 | 与 GORM 同源（database/sql） | 同上 | 平手 |
| 复杂 SQL 表达力 | 直接写 | 退回 Raw | sqlx 胜 |
| 改表加字段成本 | 改 tag + 改列名常量 | 改 tag | GORM 略胜，差距小 |
| 换数据库成本 | 高（方言绑定） | 低（方言抹平） | GORM 胜，但用不上 |
| 行为可预测性 | SQL 全可见 | 链式可能拼出意外 SQL | sqlx 胜 |
| 学习/调试成本 | 低（就是 SQL） | 中（要懂链式映射） | sqlx 胜 |

**结论**：核心文件链路用 sqlx 合理。复杂 SQL 场景 GORM 要退回 Raw，表达力优势消失；连接池性能同源无短板；唯一的真实代价（列名同步）在当前规模可控。

## 五、Go 持久层生态全景（供参考）

| 倾向 | 代表库 | 核心信念 | Java 对应 |
|------|--------|---------|----------|
| SQL 是真相，工具生成代码 | **sqlc** | 写 SQL，生成类型安全 Go 函数 | 无完全对应（优于 MyBatis XML） |
| SQL 是真相，手动写 | **sqlx / pgx** | SQL 完全可控，薄封装扫 struct | MyBatis（XML/注解 SQL） |
| 代码是真相，框架生成 SQL | **GORM / ent** | 链式 API，像 ORM | MyBatis-Plus / JPA |

Go 文化整体比 Java 更偏"SQL 是真相"这一侧（显式优于隐式、性能可预测、承认 SQL 在数据层更强），但两派都活跃，不存在"用 ORM 就是反 Go 哲学"。

## 六、升级路径

**不换信念的进化方向：sqlc。** 不是跳到 GORM（换信念），而是在"SQL 是真相"这一档内升级：

```sql
-- queries.sql 里写
-- name: GetFileByID :one
SELECT * FROM files WHERE id = $1 AND deleted_at IS NULL;
```

```go
// 自动生成，类型安全，无反射，列名同步由工具保证
file, err := q.GetFileByID(ctx, id)
```

sqlc 的价值：保留 SQL 表达力（递归 CTE、RETURNING 照写），**消除"SQL 字符串 ↔ Go 类型"的手动同步**（`fileCols` 常量和 `$1..$N` 占位符都不用手写），生成时即校验 SQL 语法。

### 触发升级的条件

- **现在不升级**：表 5 张、字段稳定、`fileCols` 同步成本可控
- **升级信号**：表数量增长到 10+ 且字段频繁变更，列名同步成为真实负担
- **升级范围**：可按模块渐进，`internal/store/` 下的 repo 一个个迁移到 sqlc，不必一次性重构

### 不选 GORM 的场景判断

仅当出现以下情况才考虑 GORM/ent（换信念）：
- 业务以简单 CRUD 为主，几乎没有复杂查询
- 存在换数据库的真实需求
- 团队对 SQL 不熟，更习惯链式 API

NimbusDrive 目前三条都不满足，故维持 sqlx。

## 七、管理后台为什么用 GORM

- 管理后台以 CRUD 为主（用户列表、统计、配置），复杂查询少
- `AutoMigrate` 对管理表的 schema 演进便利
- 不在高频链路上，性能与可预测性的要求低于核心链路
- 与核心 sqlx 层隔离，互不影响

这是"分场景选型"而非"全局统一"——Java 项目里也常见核心用 MyBatis、管理后台用 Spring Data JPA 的组合。
