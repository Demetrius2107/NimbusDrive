# NimbusDrive 开发规范

> 适用于所有贡献者。基于 GitHub Flow，强调小分支、可审查的提交、永远可发布的 master。

## 一、分支策略

### 1.1 分支模型

- **`master`**：受保护，永远可发布。**禁止直接 push**，只能通过 PR 合入。
- **功能分支**：从 `master` 最新代码拉出，命名带语义前缀，开发完成后开 PR 合回 `master`。

### 1.2 分支命名

格式：`<类型>/<简短描述>`，全小写，单词用连字符分隔。

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feat/` | 新功能 | `feat/upload-chunk-merge` |
| `fix/` | bug 修复 | `fix/quota-race-condition` |
| `docs/` | 文档变更 | `docs/api-spec-share` |
| `refactor/` | 重构（不改行为） | `refactor/store-repo-split` |
| `chore/` | 构建/依赖/配置/杂项 | `chore/upgrade-go-1.26` |
| `test/` | 补充测试 | `test/store-repo` |

### 1.3 一分支一职责

- 一个分支只做一件事。混合多个无关改动的分支会被要求拆分。
- 分支生命周期尽量短（建议 ≤ 1 周），长期分支容易冲突。

## 二、提交规范（Conventional Commits）

格式：`<类型>(<范围>): <描述>`

### 2.1 类型

| 类型 | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | bug 修复 |
| `docs` | 文档 |
| `style` | 格式调整（不改逻辑） |
| `refactor` | 重构 |
| `perf` | 性能优化 |
| `test` | 测试 |
| `chore` | 构建/工具/依赖 |
| `ci` | CI 配置 |

### 2.2 示例

```
feat(store): 实现 user/file/filehash repository
fix(auth): 修复 token 过期未返回 401 的问题
docs(api): 补充分享接口 OpenAPI 片段
chore(deps): 升级 gin 到 v1.10.0
```

### 2.3 提交粒度

- 一个提交做一件完整的小事，便于 review 与回滚。
- 提交信息用中文描述，主语省略（"实现…"而非"我实现了…"）。
- 大功能拆成多个小提交，不要一个提交塞几千行。

## 三、PR 流程

1. 从 `master` 拉功能分支，开发并自测。
2. 推送到远程，开 PR → `<feature-branch>` 合入 `master`。
3. PR 描述按模板填写（变更摘要/动机/测试/影响）。
4. 至少一次自测通过（编译 + 关键链路）后再请求 review。
5. 合并方式：**Squash merge**（功能分支多提交压成 master 上一个提交）或 **Rebase merge**（保留提交历史），不用普通 merge 产生合并提交。
6. 合并后删除功能分支。

## 四、代码规范

### 4.1 Go

- `gofmt` / `goimports` 强制格式化。
- 包注释、导出符号注释遵循 godoc 规范。
- 错误处理：业务错误用 `internal/domain.BizError`，携带错误码与 HTTP 状态；底层错误用 `fmt.Errorf("...: %w", err)` 包装。
- 依赖注入：构造函数 `NewXxx(deps) *Xxx`，不使用全局单例（`logger.L` 除外，因其生命周期与进程一致）。
- 仓储层（store）用 raw SQL 手写；管理后台（adminstore）用 GORM；二者不混用。

### 4.2 前端（TypeScript / React）

- `eslint` + `prettier`（后续接入）。
- 严格模式 `strict: true`，禁止 `any`（确需时加注释）。
- 组件用函数组件 + Hooks；状态管理 Zustand，服务端状态 TanStack Query。
- 接口调用集中在 `lib/api.ts`，不在组件内裸写 fetch。

## 五、目录约定

详见 `README.md` 仓库结构。新增代码放对应层：

- 业务领域类型 → `internal/domain/`
- 数据访问（核心链路）→ `internal/store/`
- 数据访问（管理后台）→ `internal/adminstore/`
- 对象存储 → `internal/storage/`
- 缓存 → `internal/cache/`
- 配置/日志/中间件 → `internal/config/`、`internal/logger/`、`internal/middleware/`
- 跨服务共享工具 → `pkg/`

## 六、测试

- 骨架阶段以"可编译 + 关键链路手测"为验收标准。
- 接口稳定后，在独立 `test/*` 分支补单测与集成测试。
- 仓储层测试用真实 PostgreSQL（docker-compose 起本地实例），避免 mock 漂移。

## 七、发布

- `master` 每次合并即应可部署。
- 版本号用 Git tag：`v0.1.0`、`v0.2.0`，遵循语义化版本。
- 发布说明由 Conventional Commits 自动生成（后续接入）。
