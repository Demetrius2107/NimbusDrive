# 思考与提问方法论

> 这是一份个人校准卡，不是语法笔记。每次遇到代码难点卡住、或要向 AI 提问前重读一遍。
> 也可整篇贴给 AI，作为"请按此方式与我协作"的交互契约。

---

## 0. 一句话总纲

**深度的单位是"决策"，不是"特性"。学习的单位是"在困境中伸手拿工具"，不是"背完语法条目"。提问的单位是"具体到函数名和参数"，不是"帮我看看"。**

---

## 1. 四个要警惕的下意识逃避模式

这些是我反复发作的毛病，识别它们是第一步。

### 1.1 遇到具体决策点 → 滑向概念性好聊的话题
- **症状**：被问"handler 怎么判断错误类型"，答成"重试机制、指数退避、超时策略"。
- **机制**：具体的、要落到代码行的决策（errors.As 传什么参数）是难的；概念性话题（重试策略）是好聊的、不用负责对错的。下意识避难就易。
- **对策**：发现自己开始聊"策略""机制""方案"时，停下来问自己——**"我刚才被问的具体那一步，我回答了吗？"**

### 1.2 用笼统词代替具体动作
- **症状**：说"判断一下""处理一下""做个逻辑""看看能不能落进去"。
- **机制**：笼统词让思考停在概念层，不用逼自己把动词翻译成函数名。
- **对策**：每说一个笼统动词，立刻追问三连——**"用什么函数？比什么和什么？返回什么？"** 把每个动词钉到具体的函数名和变量名上。钉不下去，就是思考真的断了，不是表达问题。

### 1.3 把"第一次说不流利"误判为"我不会" → 大脑冻结
- **症状**：被问一个问题，答出 90%（函数名对、参数对、只错一个词），却给自己判"空白、不会、无从下手"。
- **机制**：脑内标准是"第一次就要流利完整用对术语"，达不到就自我审判→冻结→误把"磕巴"当"不会"。
- **对策**：**磕巴不是失败，磕巴是站在知识边缘——而知识边缘是唯一能学到东西的地方。** 已经 confidently 的语法当年也是磕巴过的。允许自己磕巴着拼。

### 1.4 "我是不是该重新系统学一遍"逃生口
- **症状**：卡在一个具体函数怎么用，转头问"是不是我 Go 语法没学系统、要不要重新学一遍"。
- **机制**：从具体的、难的、要对错的点，滑向宏大的、永远聊不完、不用对错的"重新学习"话题。这跟 1.1 是同一个逃避，升级版。
- **对策**：**系统性学习是无穷坑——语法永远学不完，而你真正缺的那个点永远埋在第一千个条目底下。** 缺某个小语法点（var 声明、& 取址），在用到时当场学、当场用，比背一遍记得牢十倍。我 deeply 懂 interface，是因为在上下文里拆过它，不是背过教程。

## 2. 思考习惯：四条要主动练的

### 2.1 问题优先，不是特性优先
- ❌ 特性优先："演示一下 interface" → 大脑空白，因为要从"interface 这个词"反推"一个需要它的情境"。
- ✅ 问题优先："getConfig 明天要支持 Redis 和文件两个来源、不改调用方，参数该写成什么类型？" → 困境逼你伸手去拿语法。
- **原则**：语法是伸手去拿的工具，不是要凭空演示的对象。学一个新概念后，立刻找一个"什么时候会想拿它"的具体情境。

### 2.2 每个笼统词都要钉到函数名
- 把"判断"翻译成 `errors.Is(err, target)` 或 `errors.As(err, &target)`。
- 把"处理错误"翻译成 `return err` / `fmt.Errorf("...: %w", err)` / 在这层吃掉。
- 钉不下去 = 思考断了，不是嘴笨。从断点处接，不要绕开。

### 2.3 把"我不懂"拆解到行号 / 符号级
- ❌ "这一段我不理解。"
- ✅ "`*DuplicateUserError` 的 `*` 是什么？为什么只返 error 不返 result？`errors.As(err, &dupErr)` 里 dupErr 调用前是 nil，它怎么被填上的？"
- **从"我不懂"到"我具体不懂哪一行哪一个符号"——这就是从飘到具体。** 这一步本身就是在练肌肉。

### 2.4 检索策略 > 记忆
- 专业程序员不背 errors.As 的签名，用到时 `go doc errors` 或查文档。
- 真正的能力链：**遇到情况 → 意识到"我需要一个干 X 的函数" → 去标准库/文档找 → 读签名 → 用起来**。30 秒完成，这是标准操作。
- 空白时做两件事：① 用大白话说出想干嘛；② 问自己"标准库有没有专门干这个的函数？"然后去翻。

## 3. 读代码：换掉 Java 的"高深探测器"

### 3.1 Go 的深度故意看起来不深
- Java 的"高深"长这样：层层抽象、继承体系、设计模式、注解魔法、反射元编程。
- 带这套探测器扫 Go 代码，扫到扁平函数、几行 struct、一堆 `if err != nil` → 读数为零 → 下结论"没深度"。
- **这是误读。** 好的 Go 代码就是平的、无聊的、一屏读完的。深度不在语法精巧，在设计决策。

### 3.2 带这三个问题读任何 Go 代码
1. **谁依赖 interface、谁依赖具体类型？为什么这里选 interface？**
2. **这条 `if err != nil` 链，错误最终在哪一层被处理？为什么是那层？（透传 / 包上下文 / 吃掉）**
3. **这段并发用了 channel 还是 mutex？为什么不用另一个？**

每个 `if err != nil`、每个 interface 参数、每个 receiver 选择，都是一个刻意的决策。读不出深度，是因为没在问决策，只在扫语法。

### 3.3 对照 Java 理解差异（迁移学习）
- interface：Java `implements` 是名义类型（靠名字）；Go 是结构类型（靠方法形状匹配，编译期在使用处检查）。代价是"从实现反查接口"更难，工具补。
- error：Java 异常是自走控制流（throw 自动沿栈飞）；Go error 是惰性值，每往上一层要人手写 `return err` 推一次。
- receiver：Java 只有引用；Go 要决定每个方法挂 `T`（值，拿副本）还是 `*T`（指针，拿原对象）。改对象→指针，只读→值或指针（大 struct 用指针避免复制）。

## 4. 提问 AI：三段式 + 全局画像

### 4.1 单次提问用"背景 + 约束 + 产出"三段式
```
背景：我在写 Go，saveUser 返回 *DuplicateUserError。
目标：handler 要判断 err 是不是这个类型，是的话返回 HTTP 409。
约束：只用 errors.As，不要 try/catch（Go 没有）。
产出：从 err := saveUser(u) 开始的完整代码，带逐行注释。
```
每段作用：背景说语言+场景；目标说要什么结果；约束划掉不要的（防 AI 给 Java 风格答案）；产出明确形式。

### 4.2 多轮提问先给全局画像
```
我是 Java 转 Go 的新手。NimbusDrive 是我的 Go 项目，涉及 MinIO/Postgres/outbox/cron。
学过基本语法但缺实战感。给我讲解时请：
1. 每个 Go 特性对照 Java 写法说明差异；
2. 代码示例不超过 30 行，带逐行注释；
3. 不只讲语法，讲"什么时候会想伸手拿这个"；
4. 我用笼统词时，逼我具体到函数名和参数，别替我填空。
```
后续提问引用这个上下文，不再重复。

### 4.3 具体到行号，不要"帮我看看"
- ❌ "帮我看看这段 Go 代码"（AI 瞎猜：找 bug？优化？讲原理？）
- ✅ "`errors.As(err, &dupErr)` 这行，如果 err 被 `fmt.Errorf("%w", err)` 包过一层，还能匹配到吗？讲讲 Unwrap 机制。"

## 5. 学习的递进：从填空到自主

不要一上来就要求"从零写出完整代码"。按这个梯度练同一块肌肉：

1. **填空级**：脚手架给全，只填关键的两个词（如 `var ftle _____` 和 `errors.As(err, _____)`）。验证"我认识这个模式"。
2. **半自主**：撤一半脚手架，照着刚填过的形状套到新场景（换类型名、换业务）。
3. **全自主**：从 `err := xxx()` 开始整段写出来。
4. **读真实代码**：拿自己项目的代码，用第 3 节的三个问题拆，把抽象知识焊到真实代码上。

**从读到写的桥只能用手指搭。** 读十篇教程不如亲手填两个空、再亲手写一遍。

## 6. 自检清单（卡住时过一遍）

- [ ] 我是在回答**被问的那个具体问题**，还是滑到了一个好聊的话题？
- [ ] 我说的"判断/处理/做个逻辑"，能说出**具体函数名和参数**吗？说不出来=思考断了，从断点接。
- [ ] 我是不是把"第一次磕巴"当成了"我不会"？——90% 对、10% 错一个词，不是空白。
- [ ] 我是不是又在想"重新系统学一遍"？——缺的点当场学当场用，不重新背。
- [ ] 我提问时具体到行号/函数了吗？还是"帮我看看"？
- [ ] 读代码时我问了"为什么这里用 interface / 错误在哪层处理 / 并发用什么"吗？还是只扫了语法？
