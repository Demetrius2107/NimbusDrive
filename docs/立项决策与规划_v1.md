## 一、项目定位（已确认）

- **产品形态**：云存储系统，核心能力为文件存储与传输（上传 / 下载）
- **目标用户**：个人 C 端 + 团队协作组（轻量协作，不做大企业 OA 级）
- **核心差异化**：
  1. **开放协议尽可能多支持**：WebDAV / S3 / Magnet(BT) / HTTP / FTP / IPFS 开箱即用
  2. 轻量干净：无广告、无播放器绑架、无弹窗，回归存储工具本质
  3. 速度体验：分块上传、断点续传、多线程下载、不玩"免费限速 + 会员加速"套路
  4. 可自托管 + 开源（Apache 2.0）
- **红线（不变）**：不逆向任何平台私有协议、不做分享链接解析、不绕开会员限速、不做盗版资源搜索/聚合

### 2.3 关键洞察

1. **PikPak 证明**：以"磁力/离线下载"为核心卖点的网盘可以合法运营——前提是海外服务器、付费模式、不做资源搜索聚合。
2. **坚果云证明**：国内用户愿意为"WebDAV + 稳定 + 轻量"付费，这正是本项目最直接的对标。
3. **本项目差异化定位** = PikPak 的协议广度（剔除其版权灰色操作）+ 坚果云的轻量与开放（继承其 WebDAV 正统性）。

## 三、磁力/BT 决策（修订：保留，分级实施）

### 3.1 为什么此前建议"砍"（风险，依然成立）

| 风险 | 说明 |
|------|------|
| 法律/监管 | BT 下载与盗版内容强关联；国内服务器 + ICP 备案后，服务端 BT 下载器是内容安全监管重点对象；下载的侵权内容存在**平台服务器**上 = 平台持有侵权副本，责任比用户本地重 |
| 成本 | 离线下载是带宽 + 存储双大户，直接冲击成本模型 |
| 产品气质 | 纯存储工具 vs 内容获取工具，定位上存在张力 |

### 3.2 修订决策：保留，但分级 + 前置条件

鉴于定位"开放协议尽可能多支持"，磁力**保留**，但必须满足以下前置条件：

| 条件 | 要求 |
|------|------|
| 优先级 | P1/P2 后置，**不进 MVP** |
| 部署 | 下载节点部署海外（学习 PikPak），国内仅做 Web 传输与访问 |
| 输入 | 仅接受**用户主动输入**的磁力链接；不做资源搜索/热门榜/推荐 |
| 合规 | DMCA/版权投诉机制 + 哈希黑名单 + 单任务大小限制 |
| 工程 | 下载任务状态机、配额、限速、日志纳入设计 |

**结论**：磁力不做在 MVP，作为差异化功能在 P1/P2 阶段按上表条件落地。

## 四、技术栈选型（Go + React，框架层分析）

### 4.1 总体技术栈

| 层级 | 选型 | 说明 |
|------|------|------|
| 后端语言 | Go | 已确认 |
| 前端语言 | TypeScript + React | 已确认 |
| 端架构 | **客户端 / 服务端 / 管理端 三端** | Web 客户端（用户端）+ 服务端（后端 API）+ 管理端（管理后台） |
| 元数据库 | PostgreSQL 16 | JSONB、递归 CTE、LATERAL JOIN |
| 缓存 | Redis 7 | 秒传缓存、会话、限流、分享缓存 |
| 对象存储 | MinIO（自托管）/ 阿里OSS（备选） | S3 兼容，预留直传能力 |
| 部署 | Docker + Docker Compose | MVP 起步，K8s 后置 |
| 开源协议 | **Apache 2.0** | 已确认，不用 MIT |

### 4.2 后端 Web 框架：Gin vs Hertz（待二选一）

| 维度 | Gin | Hertz (CloudWeGo) |
|------|-----|-------------------|
| 生态/中间件 | **极丰富，最成熟** | 核心齐全，追赶中 |
| 纯 HTTP QPS | 高 | **更高**（netpoll，约高 20-40%，网盘场景无感知差异） |
| 大文件流式 | 标准库处理 | **Request Stream 优化**，上传内存控制更好 |
| API 风格 | 标准 | **几乎照抄 Gin**，切换成本极低 |
| 文档/社区 | **全球资料最多，AI 训练语料最全** | 中文社区活跃，字节背书 |
| 学习价值 | 一般 | **更高**（netpoll 原理） |

**网盘场景关键判断**：瓶颈在带宽/存储/对象存储，不在 HTTP 框架 QPS，框架差异对业务无感知。

**结论（已决策，2026-08-16 修订）**：后端采用 **Gin + Hertz 双服务混用**，按职责边界拆分为两个服务——**Gin（APIServer）**承载用户/鉴权/管理端/配额/文件元数据 CRUD（GORM 友好、中间件生态最全）；**Hertz（TransferServer）**承载上传/下载/分块与 Range 传输（发挥 netpoll + Request Stream 的流式优势）。两服务共享 `internal/` 公共包（领域模型、store、storage、cache、config），中间件因 Context 类型不同各自实现薄层。理由：在业务无感的前提下兼顾 Hertz 的学习价值与 Gin 的生态成熟度；服务边界、数据所有权与跨服务交互方式详见《设计文档》。

### 4.3 数据库访问层

| 方案 | 适合网盘？ | 推荐度 | 理由 |
|------|-----------|--------|------|
| **sqlx + pgx** | 非常适合 | ⭐⭐⭐⭐⭐ | raw SQL + 结构体映射；秒传查询、递归 CTE（目录树）直接手写 SQL |
| **GORM** | 管理后台适合 | ⭐⭐⭐⭐ | 重型功能用不上，但**管理后台 CRUD 效率高**，引入用于管理端 |
| ent | 适合复杂关系 | ⭐⭐⭐ | 类型安全、代码生成，但学习成本高，暂不引入 |
| bun | 现代轻量 | ⭐⭐⭐ | uptrace 出品，生态略新，暂不引入 |

**结论（已决策）**：**sqlx + GORM 双引入**——
- **核心链路（用户端）**：sqlx + pgx，raw SQL 手写（秒传查询、递归 CTE 目录树、文件哈希去重）
- **管理端（管理后台）**：GORM，管理类 CRUD 快速实现
- 职责边界：用户核心操作走 sqlx 保证可控与性能；管理后台操作走 GORM 保证开发效率，互不混用。

### 4.4 前端 React 框架与库

| 层面 | 候选 | 推荐 | 理由 |
|------|------|------|------|
| 构建 | Vite | **Vite 5** | 快、TS 一等公民 |
| 路由 | React Router v7 / TanStack Router | **React Router v7** | 成熟、资料多 |
| 客户端状态 | Zustand / Redux Toolkit / Jotai | **Zustand** | 轻量，上传队列/文件树状态适合 |
| 服务端状态 | TanStack Query | **TanStack Query v5**（必选） | 文件列表缓存、失效、重试、乐观更新 |
| UI 组件 | Ant Design 5 / MUI / shadcn-ui+Tailwind | **Ant Design 5** | Tree/Upload/Table/Progress 组件全，网盘管理类场景契合，中文文档 |
| 上传 | 原生 XHR + Web Worker + spark-md5 | **自研控制** | 分块上传、并发控制必须自己掌控，不依赖现成组件 |
| 虚拟滚动 | @tanstack/react-virtual | **推荐** | 万级文件目录不卡顿 |
| 图表 | ECharts | ECharts | 空间/流量可视化 |

**结论**：React 18/19 + TS + Vite + React Router v7 + Zustand + TanStack Query + Ant Design 5 + 自研分块上传。
